# Phase 1.1 完了報告

実施日: 2026-10-11（Asia/Tokyo）

## タブ排他ロックの原因

通常版Chromeの開発サーバーで、単一タブでも警告が残る現象を再現した。旧実装の `navigator.locks.request` に一時的な診断ログを付けた結果、次の順序を確認した。

```text
request { ifAvailable: true }
request { ifAvailable: true }
grant true
grant false
最終状態: held = [], pending = []
画面: 「別のタブが編集中です…」
```

開発時のReact StrictModeはEffectのsetup→cleanup→setupを実行する。旧実装はcleanup時に取得待ち要求を取消せず、古い要求が一瞬ロックを取得してすぐ返す間に、新しい `ifAvailable` 要求が競合して `null` を受け取っていた。その後ロックが空いても再取得しないため、画面だけが永続的な競合状態になった。

加えて、API例外もすべて「別タブが編集中」に分類しており、競合と取得エラーを区別できなかった。以前のブラウザテストは本番ビルドのみを対象としていたため、StrictModeの開発時再実行を検証していなかった。

Reactの再実行の仕様は [React公式](https://react.dev/reference/react/StrictMode)、ロックのキュー・キャンセル・クライアント終了時の解放は [Web Locks仕様](https://www.w3.org/TR/web-locks/) を参照した。

## 修正

- 取得処理を `EditorLockController` とReact用フックに分離。`ifAvailable` の一回判定を、AbortSignal付きの排他キュー要求に変更。
- 要求ごとに所有者IDを生成し、現在の要求・有効フラグ・実際に取得した排他ロックが一致する場合だけ編集可能とする。古いコールバックは無視する。
- cleanup・`pagehide`で取得待ち要求を取消し、取得済みの場合はローカルの書込権限を即座に失効させて保持Promiseを解決する。ページ復帰時は再取得する。
- 所有タブの終了後、待機タブが自動取得。取得後、ロックを保持したまま最新保存データを再読込し、その後に操作を有効化する。
- AppStoreの操作入口にも所有権ガードを追加。古いイベントハンドラーや通知チェックからの書込みも拒否する。既存のrevision検証は維持。
- ロックAPI未対応・API障害・データ読込失敗は競合と分けて表示し、編集を停止する。API障害は再試行可能。

ロック情報はlocalStorageに永続化していない。古い要求はAbortSignalと所有者IDで判定・無効化する。異常終了したタブの実ロックはブラウザが解放し、キューの次のタブが安全に取得する。ブラウザ全体がクラッシュした場合も、再起動後に実ロックを新規取得する。時刻だけで「古い」と判定して生存中の所有者から奪取する処理や、`steal`は使用しない。

`pomolog.document`の保存キー・schemaVersion 1・履歴形式は変更していない。localStorageの全削除・履歴削除・ロック回避は行っていない。

## UI改善

タイマー画面の順序を次に変更した。

1. ページタイトル
2. 集中タイマーと学習内容・問題数カウンター
3. 今日の集中時間・達成セット・問題数の集計
4. メモ・最近の履歴・保存と通知の情報

PCはタイマーと学習入力を横並び、スマホは縦並びを維持。メモを集計の下に移すことで、右カラムの高さに引かれてタイマーカードが伸びる問題も解消した。上部余白、ダイヤルサイズ、操作と説明の間隔を縮め、1366×768・1280×720の表示範囲内に一時停止・休憩・セット終了を収めた。

ロゴ画像は余白と画像内の文字を含んだ正方形だったため、旧表示では時計マーク自体が小さくなっていた。原本・公開用画像は変更せず、CSSの表示枠で時計マークを切り出した。PCは50×60px、スマホは30×36pxの枠にマークを表示し、隣のPOMOLOG文字と組み合わせた。配色と既存のカード・入力部品は維持した。
